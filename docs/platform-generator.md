# The platform generator

Status: **draft for review** (Phase 0). Tool details marked **[verify]** are
to be confirmed in Phase 2 against the pinned AMD release.

Rule (decisions, 2026-09-30): no board-specific code is written by hand.
Everything that depends on the target is generated from the platform
specification Vivado and Vitis provide for it. Supporting a board means
pointing the generator at its platform; `FPGA-Hardware/boards/<board>/` holds
only what the generator wrote.

## Inputs: what Vivado and Vitis already know about a target

| input | from | gives |
|---|---|---|
| **board files** | Vivado's board store (the KV260 is a Xilinx-provided board, with its SOM and carrier) | the part (`xck26-sfvc784-2LV-c`), connectors and pins, and the PS preset: DDR configuration, MIO, clocks |
| **part data** | Vivado's device database | resources: LUT, FF, DSP, BRAM, URAM counts; speed grade; I/O banks |
| **exported hardware platform (XSA)** | Vivado, from a generated block design | the address map, the PS configuration actually applied, `psu_init` (the PS register settings), the bitstream |
| **system device tree** | AMD's tools from the XSA **[verify: `sdtgen`/Lopper in the pinned release]** | every device and memory region in machine-readable form |
| **Vitis platform** | Vitis, from the XSA | the target as Vitis sees it, for HLS kernels |

A board with no processing system (Genesys 2) has board files and part data
and no PS preset; the generator's output is then smaller, not different in
kind.

## Outputs, per target, all generated

1. **Platform description** for the core and Hydra: memory windows, number and
   width of memory ports, clock frequencies, interrupt numbering, resource
   counts. A generated header the HLS sources take as template parameters,
   and a machine-readable file Hydra reads.
2. **Block design** (Vivado Tcl, generated): the PS instance configured from
   the board preset, with the HP ports, the low-power port and the `pl_clk`
   outputs the contract needs; the core's and accelerator's HLS IPs; the
   generated adapters; clock and reset wiring. Vivado writes the RTL wrapper.
3. **Adapters**: the memory-port streams onto the board's ports, as HLS
   instantiated from templates with the platform description's parameters --
   instances, not hand-written code.
4. **Constraints**: pins the design uses (on the KV260, the fan PWM pin, which
   the bitstream must drive, and the Pmod), from the board files.
5. **Boot image**: on a Zynq UltraScale+ target, an FSBL generated by Vitis
   from the XSA, configured to run once on the R5, apply `psu_init`, load the
   bitstream and park; a generated BIF; `bootgen` to BOOT.BIN. **[verify]**
   whether the PMU firmware can be left out, and how BOOT.BIN is written to
   the KV260's QSPI past its stock A/B image selector.
6. **Device tree and firmware platform** for the RISC-V: memory, the uncore,
   and the board's devices the core can reach, derived from the system device
   tree and the address map.
7. **Resource and timing reports** after each stage, parsed into one summary
   (HLS `csynth.xml`, Vivado post-synthesis and post-route utilization and
   timing).

## Tool flow

Command-line only, pinned to one AMD release per project release (directives
change between releases; the classic `vitis_hls` command is gone from 2025.1):

| step | command |
|---|---|
| HLS synthesis of each IP | `v++ -c --mode hls --config <generated .cfg>` |
| C simulation, co-simulation, IP packaging | `vitis-run --mode hls --csim / --cosim / --package` |
| block design, implementation, bitstream | `vivado -mode batch -source <generated .tcl>` (non-project mode) |
| boot image | the FSBL from the XSA; `bootgen` |

The K26 is covered by the free Vivado ML Standard edition (AMD forum answer;
**[verify]** against AMD's device table).

## Where generation stops

The generator produces everything target-specific. It does not produce the
core, the uncore or the accelerator -- those are hand-written C++ (the
accelerator's configuration comes from Hydra). If generating something
turns out to need knowledge the platform specification lacks, that is
recorded in `docs/decisions.md` as a gap, not filled in by hand.
